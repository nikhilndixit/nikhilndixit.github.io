Case study 01

Pulse: one view of every customer, across every team that serves them

The problem

At my current company, everything we know about a customer sat in six systems owned by different teams: content ratings, live-session ratings, two separate support helpdesks, surveys and a reporting tool. None of them shared an ID. Answering "how are our customers experiencing every part of the product?" meant manual exports, spreadsheet stitching and several cross-functional meetings. Problems surfaced after customers had already disengaged.

Nobody had asked me to fix this. I scoped it, got data access, and built it outside my core role.

6 → 1data sources unified into one searchable profile
4–5 hrs → ~5 minto assemble a full customer picture
64automated tests on the pipeline and AI layer

How I shipped it

Each phase had to be useful on its own before the next one started.

  1. Phase 1 · Aug–Sep
    Customer ratings analysis using CSV exports to validate the value of customer feedback insights before investing in integrations, with explicit data-quality tracking to flag bad or missing records rather than silently dropping them.
  2. Phase 2 · Sep
    Live API ingestion and data standardisation into MySQL, mapping disparate sources to a shared vocabulary and validating API metrics against CSV exports to establish a reliable, unified data foundation for learner intelligence.
  3. Phase 3 · Oct
    Consolidated learner journey dashboard bringing together customer profiles, subjective feedback captured through the LMS, course progress, and evaluation metrics such as marks and grades to provide a unified view of the learner experience and outcomes.
  4. Phase 4 · Oct
    Unified learner intelligence layer combining structured journey metrics with unstructured support tickets and escalations to surface actionable insights, identify recurring pain points, and accelerate data-driven product and program decisions.
  5. Phase 5 · Oct
    LLM based conversational learner intelligence enabling users to query individual learners, programs, or cohorts using customer emails or natural-language prompts, generating tailored dashboards and concise summaries to translate complex data into actionable insights.

Product decisions

The AI never produces a number

SQL fetches every figure. The model only reads the request, picks components from a fixed list and writes a summary. Any number in that summary that doesn't match the data hides the summary.

Prove value before plumbing

The first dashboard ran on CSV uploads. APIs, scheduling and storage came only after people found the views useful.

Measure the model before choosing it

A 30-prompt evaluation set with a pass bar: plan correct 90% of the time, valid layout every time, zero invented numbers. The plan is to pick the smallest model that passes.

Privacy by design

Runs on a local open-source model. Code finds customer emails and masks them before anything reaches the model.

Where it stands

  • Working end to end as a pilot on my machine, on real data.
  • Next: run the model comparison, put it in front of 2–3 users for a week, then find it a hosted home and an engineering owner.
  • Later: log which issues were actioned and how they turned out, so Pulse can start suggesting fixes from past outcomes.

The public repo is a standalone version on synthetic data. It contains no company data, schema or system names. See it on GitHub.
